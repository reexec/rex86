# #40 작업 로그 : Zen 5의 CMPS 원본 #GP 판정 / #40 work log : judging Zen 5's CMPS source #GP

## 2026-10-10

호스트: AMD Ryzen 5 5600X(Zen 3) 12 스레드, Linux. 앞선 작업들의 기계와 다르다.

- **발견**: v0.0.20 머지 때 `main` push의 smoke 캠페인([run 38014191828](https://github.com/reexec/rex86/actions/runs/38014191828))에서 정수 fuzz(i386, 예열 기본값) shard 1이 불일치 1건으로 실패했다. 러너는 AMD EPYC 9V45(Zen 5)였다. artifact의 `int-1.rxt`를 `rex86_trace --dump`로 보면 `64 67 A6`(FS 접두어, 16비트 주소 CMPSB)이고, 원본 FS는 null 선택자, 목적지 DI는 0xFFEF로 매핑 밖이다. 기대값은 #GP, 코어는 #PF였다.
- **원인**: Zen 5가 CMPS의 원본을 먼저 읽는 제조사 차이다. 기존 판정 `SourceFirstCompareFault`는 두 폴트가 모두 #PF인 경우만 다뤘다(설계 문제 절).
- **사용자 결정**: 이슈 #40을 만들고 다음 task로 진행.
- **구현**: `tests/host/linux/int_fuzz.cpp`에 `SourceSegmentFirstCompareFault`를 더하고 `VendorDeviation`에 이었다(설계 결정 2). 원본 세그먼트는 Zydis 피연산자의 `mem.segment`로 찾고, trace의 선택자 배열 순서(ES, CS, SS, DS, FS, GS)가 Zydis의 레지스터 순서와 같음을 헤더에서 확인했다. 코어는 바뀌지 않는다.
- **판정 경로 확인**(scratchpad의 작은 검사 프로그램으로 `int-1.rxt`를 재생):
  - 기록된 기대값(#GP): 불일치.
  - 기대값을 #PF로 바꾸고 주소 0xFFEF(목적지 첫 바이트): 일치. 0xFFF0, 0x10000, 0x1131C(원본): 불일치.
- **로컬(Zen 3)**:
  - i386 Release와 Debug를 `-Werror`로 빌드했다. i386 Debug ctest 8/8.
  - 실패했던 smoke 시드 30000000~30000003 각 2만 건: 모두 불일치 0, `vendor_deviations` 0. Zen 3은 이 사례에서 코어와 같이 #PF를 낸다.
  - 1,000만 건(10 shard × 100만, 시드 4000000~4000009): 불일치 0, `vendor_deviations` 106. 100만 건당 10.6건으로, 이미 알려진 Zen 3 BOUND 이탈의 비율(250만 건에 32건)과 비슷하다.
- **Zen 5(CI)**: 이 브랜치에서 `workflow_dispatch`로 smoke 캠페인을 돌렸다. 같은 ref의 실행은 앞선 것을 취소하므로, 처음 한꺼번에 보낸 셋 가운데 둘은 취소됐다.
  - [run 38025019817](https://github.com/reexec/rex86/actions/runs/38025019817): 9개 작업 녹색. 예열 0 작업이 9V45에 걸려 불일치 0, `vendor_deviations` 3, 6, 10, 2. 예열 기본값 작업은 EPYC 9V74에 걸려 `vendor_deviations` 0이었다.
  - [run 38025199518](https://github.com/reexec/rex86/actions/runs/38025199518): 예열 기본값 작업이 9V45에 걸렸다. 시드 30000001이 불일치 0, `vendor_deviations` 4다(수정 전 같은 러너 종류에서 불일치 1, `vendor_deviations` 3). 실패했던 사례가 제조사 차이로 옮겨 갔다. 나머지 시드도 5, 0, 3으로 수정 전과 같다.
  - **확인됨(관측)**: EPYC 9V74에서는 같은 시드 넷의 `vendor_deviations`가 0이다. 이 러너는 CMPS와 BOUND 모두 코어(Intel 순서)와 같게 동작한다. 9V74의 세대는 이 저장소에서 확인하지 않았다(**미확정**).

*Found: the smoke campaign of the `main` push at the v0.0.20 merge (run 38014191828) failed in the integer fuzz (i386, default warm-up), shard 1, with one mismatch on an AMD EPYC 9V45 (Zen 5); `rex86_trace --dump` on the artifact's `int-1.rxt` shows `64 67 A6` (FS prefix, 16-bit addressing CMPSB) with the null FS selector on the source and DI = 0xFFEF outside the mapping, expected #GP against the core's #PF. Cause: Zen 5 reading the CMPS source first, while the existing `SourceFirstCompareFault` handled only two #PFs. The user decided to open issue #40 and proceed. Implemented `SourceSegmentFirstCompareFault` in `tests/host/linux/int_fuzz.cpp`, chained into `VendorDeviation` (design decision 2); the source segment comes from the Zydis operand's `mem.segment`, and the trace's selector order (ES, CS, SS, DS, FS, GS) was checked against Zydis's register order in its header; the core is unchanged. The verdict path, replaying `int-1.rxt` in a small scratchpad program: the recorded #GP expectation mismatches; a #PF at 0xFFEF (the destination's first byte) matches; 0xFFF0, 0x10000 and 0x1131C (the source) do not. Locally (Zen 3): i386 Release and Debug build with `-Werror`, i386 Debug ctest 8/8; the failing smoke seeds 30000000-30000003 at 20,000 each give zero mismatches and zero deviations, Zen 3 raising #PF like the core; 10M cases (10 shards × 1M, seeds 4000000-4000009) give zero mismatches and 106 deviations, 10.6 per million, close to the known Zen 3 BOUND rate (32 in 2.5M). Zen 5 (CI), through `workflow_dispatch` on this branch (same-ref runs cancel earlier ones, so two of the three first sent were cancelled): run 38025019817 green in nine jobs, the warm-up 0 job on a 9V45 with zero mismatches and 3, 6, 10 and 2 deviations, the default job on an EPYC 9V74 with zero deviations; run 38025199518 put the default job on a 9V45, where seed 30000001 gives zero mismatches and 4 deviations (one mismatch and 3 deviations before the change on the same runner kind), so the failing case moved into the deviations, and the other seeds keep 5, 0 and 3. Confirmed (observation): on the EPYC 9V74 the four seeds give zero deviations, that runner behaving like the core (Intel order) on CMPS and BOUND; its generation was not checked here (unresolved).
