## 2026-10-12 ~ 2026-10-13

호스트: AMD Ryzen 5 5600X(Zen 3) 12 스레드, Windows 11 Pro, Visual Studio 2026(MSVC, x64 Release), emsdk 3.1.74(Node 24.19.0), Playwright 1.63.0(Chromium 153.0.8010.12, Firefox 155.0). 브랜치는 `work/i049-wasm-module-batching`(main `f2e4759`에서).

*Host: AMD Ryzen 5 5600X (Zen 3), 12 threads, Windows 11 Pro, Visual Studio 2026 (MSVC, x64 Release), emsdk 3.1.74 (Node 24.19.0), Playwright 1.63.0 (Chromium 153.0.8010.12, Firefox 155.0); branch `work/i049-wasm-module-batching` (from main `f2e4759`).*

- **사전 실험**(설계 결정 1): Firefox에서 함수 1, 16, 64개짜리 모듈 모두 16,349개째에 실패했다. 한도는 모듈 수에 걸리고, wasm 32 KB까지는 모듈 크기와 무관했다. 51 KB 모듈에서는 8,220개였다.
- **구현**:
  - 공개 계약: `TranslationOptions`의 `blocks_per_module`(16), `batch_wait`(4,096), `max_modules`(4,096), `TranslationStats`의 `modules_submitted`, `modules_evicted`.
  - 실행기: 상태 `kQueued`와 묶음 대기열, 묶음 하나에 티켓 하나, 모듈 기록과 FIFO 축출. `Backend::Compile`은 번역 배열을 받고, `BatchCapacity`를 더했다.
  - wasm 백엔드는 묶음을 함수 여럿의 모듈 하나로 만든다. 번역 강제 `WASM`은 `blocks_per_module = 1`이다.
  - IR 차등은 wasm 비교를 `--wasm-batch`(16)개씩 묶는다. 벤치마크에 `blocks` 워크로드(블록 24,576개, `mixed`는 그대로 다섯 커널)와 옵션 셋, 모듈 보고를 더했다. 웹 어댑터는 설치 바이트, 함수, 거절을 센다.
  - `tests/host/web/module_limit.{html,js}`와 `drive.mjs --module-limit`, CI 단계 "Module limit probe", Pages 사이트에 탐침 파일. 브라우저 모음의 IR 차등 2만 건, 기본 대기 1초.
- **발견 1**(wasm32 단위 테스트): 묶음 IR 차등이 불일치를 냈다(묶음 2에서 5,000건 중 3건, 1에서는 0). 원인은 차등 도구였다. 사례마다 바뀌는 `features.cmov`를 묶음이 모인 뒤의 값으로 인터프리터에 넘겼다. 사례의 `Features`를 함께 저장해 고쳤고, 그 뒤 불일치 0이다. 생성 코드의 결함은 아니었다.
- **발견 2**(`blocks` 워크로드): 처음에는 블록마다 `jmp short +0`을 두었는데, 번역이 거의 일어나지 않았다(평가기에서 14블록). 목적지가 바로 다음 명령인 점프는 인터프리터의 블록 루프가 분기로 보지 않으므로, 블록 머리마다 번역 실행기로 돌아오지 않는다. `int3` 한 바이트를 건너뛰게 고쳤다.
- **발견 3**(예산): 처음 구현은 평가기에도 예산(당시 기본 1,024)을 적용해, 블록 1개짜리 "모듈" 1,024개에서 축출이 헛돌았다(28만 번). 예산과 묶음을 `kWasm`에만 두고, 기본 예산을 4,096으로 올렸다.
- **발견 4**(축출의 헛돌기): Node에서 `blocks`를 묶음 1, 예산 4,096으로 돌리자 작업 집합이 예산을 넘어 모듈 76만 개를 설치했고 0.42 MIPS였다(인터프리터 3.0). 축출된 블록의 재번역 문턱을 2배씩(최대 64배) 올리는 억제를 넣었다. 같은 조건에서 11만 5천 개, 1.7 MIPS다(설계 결정 3).
- **측정**(기록 3.1절): Firefox에서 `blocks`는 묶음 없이 16,339개 설치, 8,241개 거절, 0.34 MIPS였고, 기본값으로 1,537개, 거절 0, 7.3 MIPS였다. 묶음 크기 1, 4, 16, 64와 `batch_wait` 256, 4,096, 65,536을 Node, Chromium, Firefox에서 세 번씩 번갈아 재서 16과 4,096을 골랐다.
- **검증**:
  - 단위 테스트: Windows x64 Release `checks=2266 failures=0`(새 `translate_batch_test`: 꽉 찬 묶음, 부분 묶음, 대기 중 무효화, 비동기 묶음, 개수 불일치, `Flush`, 예산 축출, 축출 억제).
  - ctest: Windows x64 Release 6/6, wasm32(Node) 7/7(실제 웹 어댑터로 묶음, 축출, 비동기 묶음을 보는 `WasmBatchTests` 포함), 번역 강제 `WASM` 7/7(`-DREX86_WARNINGS_AS_ERRORS=ON`).
  - Node에서 `rex86_irdiff --cases 500000 --seed 2490000000`: 형태와 블록 모두 불일치 0, 모듈 38,385개.
  - 브라우저 모음: Chromium과 Firefox 10/10, 재시도 0. Firefox는 대기 0으로 세 번 모두 10/10, 재시도 0.
  - 탐침: Chromium `modules=40000 ended=cap`, Firefox `modules=16349 ended=refused`.

*Spike (design decision 1): in Firefox modules of 1, 16 and 64 functions all failed at the 16,349th; the limit counts modules, independent of module size up to 32 KB of wasm, 51 KB modules stopping at 8,220. Implemented: the public contract's `TranslationOptions::blocks_per_module` (16), `batch_wait` (4,096) and `max_modules` (4,096), and `TranslationStats::modules_submitted` and `modules_evicted`; in the runtime the `kQueued` state and batch queue, one ticket per batch, module records and FIFO eviction, `Backend::Compile` taking an array of translations and `BatchCapacity` added; the wasm backend makes a batch into one module of several functions, forced `WASM` using `blocks_per_module = 1`; the IR differential batches its wasm comparisons `--wasm-batch` (16) at a time, the benchmark gains the `blocks` workload (24,576 blocks, `mixed` keeping its five kernels), the three options and module reporting, and the web adapter counts installed bytes, functions and refusals; `tests/host/web/module_limit.{html,js}` with `drive.mjs --module-limit`, the CI step "Module limit probe" and the probe files on the Pages site; the browser suite's IR differential at 20,000 cases and a 1-second default wait. Finding 1 (wasm32 unit tests): the batched IR differential found mismatches (3 in 5,000 at batch 2, none at 1), the tool's fault: it passed the interpreter the per-case `features.cmov` as it stood after the batch had gathered; storing each case's `Features` fixed it, with no mismatch since, the generated code not at fault. Finding 2 (the `blocks` workload): its first version put `jmp short +0` in each block and hardly translated (14 blocks on the evaluator), since the interpreter's block loop does not take a jump to the very next instruction for a branch and so does not come back to the runtime at every head; the blocks now jump over one `int3` byte. Finding 3 (the budget): the first version applied the budget (then 1,024 by default) to the evaluator too, which thrashed at 1,024 one-block "modules" (280,000 evictions); batching and the budget now apply to `kWasm` alone, and the default budget rose to 4,096. Finding 4 (eviction thrashing): on Node `blocks` with 1-block batches and a 4,096 budget, its working set beyond the budget, installed 760,000 modules at 0.42 MIPS (interpreter 3.0); a backoff doubling an evicted block's re-translation threshold (up to 64 times) brought that to 115,000 modules at 1.7 MIPS (design decision 3). Measured (record section 3.1): in Firefox, `blocks` installed 16,339 modules, refused 8,241 and ran at 0.34 MIPS without batching, and with the defaults installed 1,537, refused none and ran at 7.3; batch sizes 1, 4, 16 and 64 and `batch_wait` 256, 4,096 and 65,536 were measured three times interleaved on Node, Chromium and Firefox, choosing 16 and 4,096. Verification: unit tests `checks=2266 failures=0` on Windows x64 Release (the new `translate_batch_test`: full and partial batches, invalidation while queued, asynchronous batches, a count mismatch, `Flush`, eviction at the budget and its backoff); ctest Windows x64 Release 6/6, wasm32 (Node) 7/7 (with `WasmBatchTests` checking batches, eviction and asynchronous batches through the real web adapter) and forced `WASM` 7/7 (`-DREX86_WARNINGS_AS_ERRORS=ON`); `rex86_irdiff --cases 500000 --seed 2490000000` on Node with no mismatch in forms or blocks over 38,385 modules; the browser suite 10/10 with no retry on Chromium and Firefox, Firefox also 10/10 with no retry three times with no wait; the probe printing Chromium `modules=40000 ended=cap` and Firefox `modules=16349 ended=refused`.*

## 2026-10-13: 머지 전 CI / CI before the merge

- **CI 실패**([실행 38275117098](https://github.com/reexec/rex86/actions/runs/38275117098), 커밋 `fb14ea9`): wasm32 작업의 번역 강제 `WASM` 단계에서 `rex86_unit_tests`와 `rex86_bench_smoke`가 Node 힙 부족(`Ineffective mark-compacts near heap limit`, 약 3.3 GB)으로 끝났다. 나머지 작업(`browsers` 포함)은 녹색이었다.
- **원인**: 번역 강제는 문턱 0, 묶음 1, 예산 4,096이다. 축출 억제가 `threshold << evictions`라 문턱 0에서는 0이었다. 그래서 `blocks` 워크로드(블록 24,576개)가 바퀴마다 블록을 모두 다시 설치했다. 이 작업은 Node를 따로 설치하지 않아 러너의 Node 20을 썼고, #50에서 본 것처럼 Node 20은 생성 모듈이 많으면 메모리가 계속 는다. 로컬(Node 24)에서는 통과했으나 147초가 걸렸다.
- **수정**: 억제의 기준을 `max(threshold, 1)`로 했다(축출 뒤 1 << n 진입). 단위 테스트에 문턱 0의 억제를 더하고, 예산 테스트의 기대를 고쳤다. CI wasm32 작업에 `actions/setup-node` Node 24를 더했다(캠페인의 wasm-translate와 같음).
- **검증**: 단위 테스트 `checks=2272 failures=0`, ctest Windows x64 Release 6/6, wasm32 7/7, 번역 강제 `WASM` 7/7(147초에서 약 36초로).
- **CI**([실행 38276824251](https://github.com/reexec/rex86/actions/runs/38276824251), 커밋 `84d7b66`): 모든 작업 녹색. 탐침은 Chromium 153 `modules=40000 ended=cap`, Firefox 155 `modules=16349 ended=refused`, WebKit 26.6 `modules=40000 ended=cap`이다. WebKit 결과를 기록 3.1절에 더했다.

*CI failure (run 38275117098, commit `fb14ea9`): in the wasm32 job's forced `WASM` step, `rex86_unit_tests` and `rex86_bench_smoke` ended with Node running out of heap (`Ineffective mark-compacts near heap limit`, some 3.3 GB), every other job (`browsers` included) green. Cause: forced translation uses a threshold of 0, 1 block per module and a 4,096 budget, and the eviction backoff `threshold << evictions` was 0 at a threshold of 0, so the `blocks` workload (24,576 blocks) reinstalled every block every lap; the job installs no Node of its own and used the runner's Node 20, whose memory grows with many generated modules as #50 found; locally (Node 24) it passed in 147 seconds. Fix: the backoff counts from `max(threshold, 1)` (1 << n entries after an eviction); the unit tests gain the backoff at a threshold of 0 and the budget test's expectation changes; CI's wasm32 job gains `actions/setup-node` with Node 24, as the campaign's wasm-translate. Verification: unit tests `checks=2272 failures=0`, ctest Windows x64 Release 6/6, wasm32 7/7 and forced `WASM` 7/7 (from 147 seconds to about 36). CI (run 38276824251, commit `84d7b66`): every job green; the probe printed Chromium 153 `modules=40000 ended=cap`, Firefox 155 `modules=16349 ended=refused` and WebKit 26.6 `modules=40000 ended=cap`, WebKit's result going into record section 3.1.*
