### 데모 엔진(설계 결정 1)

- `src/tools/demo/demo.cpp`의 C 함수 여섯과 CMake 타깃 `rex86_demo`(`-sMODULARIZE=1 -sEXPORT_NAME=createRex86Demo -sEXIT_RUNTIME=0`, `cwrap`, `UTF8ToString`, `HEAP8`). 코어 모듈은 522 KiB(534,761바이트), JS 로더는 15 KiB다.
- `demo_smoke.cjs`: 처음 판은 프레임 3개(30만 단계) 안에 바퀴가 끝나기를 요구했다. 그런데 `string`과 `mixed`는 한 바퀴가 그보다 길어(60만, 80만 단계) 바퀴 0으로 실패했다. 엔진의 결함은 아니어서, 바퀴가 끝날 때까지 최대 30프레임을 돌리게 고쳤다. 그 뒤 세 엔진 × 여덟 워크로드가 모두 verified이고, 없는 워크로드는 거절된다.

*The six C functions of `src/tools/demo/demo.cpp` and the CMake target `rex86_demo` (`-sMODULARIZE=1 -sEXPORT_NAME=createRex86Demo -sEXIT_RUNTIME=0`, with `cwrap`, `UTF8ToString` and `HEAP8`); the core module is 522 KiB (534,761 bytes), the JS loader 15 KiB. `demo_smoke.cjs` first asked for a lap within 3 frames (300,000 steps), failing `string` and `mixed`, whose laps are longer (600,000 and 800,000 steps) with no engine defect; it now runs up to 30 frames until a lap ends, after which all three engines × eight workloads verify and an unknown workload is refused.*

### Worker와 페이지(결정 2)

- `demo_worker.js`, `demo.html`, `demo.js`. 실시간 실행에서 엔진이나 워크로드를 바꾸면 다시 시작한다. 이때 앞선 고리의 늦은 프레임이 새 실행의 기록에 섞일 수 있었다. 그래서 `run` 번호를 오가게 했다. "시작 이후 MIPS"도 처음에는 최근 120프레임으로 셌는데, 전체 시간을 따로 쌓게 고쳤다.
- 화면 확인(스크린샷, Chromium): 1100 px 밝은 테마와 390 px 어두운 테마 둘 다 봤다. 휴대폰 폭에서는 조작부와 수치가 두 열로, 표가 한 열로 접힌다.
- 관찰: 짧은 실행(250,000단계 × 40프레임, wasm `alu`)의 앞 프레임은 번역과 모듈 설치가 섞여 느리다. 끝 무렵 프레임은 약 70~80 MIPS였지만 "시작 이후"는 8.3 MIPS였다. 가이드 5절에 그래프가 평평해진 뒤 읽으라고 적었다.

*`demo_worker.js`, `demo.html` and `demo.js`. Changing the engine or workload while running restarts, and late frames of the earlier loop could mix into the new run's history, so a `run` number now goes back and forth; "MIPS since start" first counted the last 120 frames and now accumulates the whole time. Checked by screenshots (Chromium) at 1,100 px in the light theme and 390 px in the dark one: at phone width the controls and readouts fold to two columns and the tables to one. Observed: a short run (250,000 steps × 40 frames, wasm `alu`) starts slow while translation and module installation mix in, its last frames near 70 to 80 MIPS against 8.3 "since start"; guide section 5 says to read the figures once the graph levels.*

## 2026-10-13 실기기: Android Chrome / Real device: Android Chrome

- 사용자가 v0.0.30 Pages의 데모를 Android Chrome 154에서 `mixed`, wasm, 프레임당 100만 단계로 7,968프레임 돌린 보고 줄을 [#62](https://github.com/reexec/rex86/issues/62#issuecomment-6146902562)에 붙였다. 결과는 ok(바퀴 11,075개 모두 검증), 최근 1초 33.4 MIPS, 코어 모듈 539 KiB, wasm 힙 16.4 MiB, 엔진 메모리 4.61 MiB(블록 54, 모듈 46)다.

- 값은 [분석](../analysis/browser-wasm.md) 5.1절에 적었다. user agent가 축소형이라 기기 모델을 알 수 없다. 측정 모드와 인터프리터의 값도 없다.

*The user pasted into #62 the report lines of the v0.0.30 Pages demo run in Android Chrome 154: `mixed` on wasm at a million steps per frame for 7,968 frames, result ok (all 11,075 laps verified), 33.4 MIPS over the last second, a 539 KiB core module, a 16.4 MiB wasm heap and 4.61 MiB of engine memory (54 blocks, 46 modules). The real-time ratio is 0.083 against the 400 MHz boards and 0.024 against the 1.4 GHz board. Against host D's desktop Chromium (`rex86_bench`, 60.5 MIPS) it comes to about 0.55, kept as an inferred comparison because the methods differ. The figures are in section 5.1 of the analysis; the reduced user agent hides the device model, and there are no measurement-mode or interpreter figures.*
