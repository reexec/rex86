# rex86 v0.0.23

wasm 번역을 실제 브라우저에서 검증했습니다. Chromium, Firefox, WebKit의 CI가 코어의 테스트 모음을 돌립니다. 메인 스레드에서 쓸 수 있는 비동기 설치 어댑터도 더했습니다. 공개 계약은 바뀌지 않습니다.

## 변경 사항

- **비동기 설치 어댑터**(#48, `src/host/web/async_wasm_module_services.h`):
  - `AsyncWebWasmModuleServices`는 `Install`에서 `kPending`으로 답하고, `WebAssembly.compile`과 `instantiate`를 시작합니다. 호스트가 프레임 사이에 `Poll(cpu)`을 부르면 끝난 설치가 `Cpu`로 넘어갑니다.
  - 결과 큐는 어댑터마다 있어, 어댑터 하나가 `Cpu` 하나를 섬깁니다. 소멸자는 넘기지 않은 결과의 테이블 칸을 돌려줍니다.
- **브라우저용 빌드**: CMake `REX86_BROWSER`와 프리셋 `web-browser-release`. 테스트 도구를 Node 파일 시스템 없이, 종료 코드를 페이지에 전하게 링크하고, trace 묶음을 싣습니다.
- **브라우저 실행기**(`tests/host/web/`):
  - 도구를 Worker에서 차례로 돌리는 페이지가 있습니다. 비동기 테스트만 메인 스레드에서 돕니다.
  - 실기기용 LAN 정적 서버와, Playwright 1.63.0으로 Chromium, Firefox, WebKit을 띄우는 드라이버가 있습니다.
  - [가이드](../guides/browser-tests.md)에 실기기 절차가 있습니다.
- **비동기 테스트** `rex86_async_test`: `Cpu` 둘이 한 프레임 루프에서 돌고, 설치가 대기 중일 때도 인터프리터로 계속 돌며, 결과가 인터프리터만 쓴 실행과 같은지 봅니다. wasm32 ctest(Node)와 브라우저 메인 스레드에서 돕니다.
- **CI**: 작업 `browsers`를 더했습니다.

## 발견

- Firefox(SpiderMonkey)는 한 프로세스에서 wasm 모듈 16,349개째부터 설치를 거절합니다. 버린 모듈의 코드 메모리는 쓰레기 수집에서만 돌아옵니다([기록](../analysis/browser-wasm.md) 3절).
- 블록 하나에 모듈 하나인 지금의 백엔드는 Firefox에서 번역이 약 1만 6천 블록으로 묶입니다. 거절된 블록은 인터프리터로 돌아 결과는 맞습니다. 묶음 설치와 모듈 수 예산은 [#49](https://github.com/reexec/rex86/issues/49)에서 다룹니다.

## 소비자 영향

- 공개 계약(`include/rex86/`)은 바뀌지 않습니다.
- 메인 스레드에서 번역을 쓰는 웹 소비자는 `AsyncWebWasmModuleServices`를 쓰고, 프레임마다 `Run` 뒤에 `Poll`을 부릅니다. Worker 소비자는 지금의 동기 어댑터를 그대로 씁니다.
- Firefox에서 번역 블록이 많은 게스트는 모듈 수 한도에 걸릴 수 있습니다(#49).
- **v0.0.22와 이 릴리스에는 [#50](https://github.com/reexec/rex86/issues/50)의 결함이 있습니다**(아래 캠페인 절). 번역을 켠 경우에만 해당합니다. 기본값인 꺼짐에서는 영향이 없습니다. 소비자의 tag 올림은 #50을 고친 patch 릴리스의 캠페인이 녹색이 된 뒤에 합니다.

## English

# rex86 v0.0.23

Wasm translation is now verified in real browsers: CI runs the core's test suite in Chromium, Firefox and WebKit. An asynchronous installer usable on the main thread joins the web adapter. The public contract does not change.

## Changes

- **The asynchronous installer** (#48, `src/host/web/async_wasm_module_services.h`): `AsyncWebWasmModuleServices` answers `Install` with `kPending` and starts `WebAssembly.compile` and `instantiate`; the host's `Poll(cpu)` between frames hands finished installations to the `Cpu`. Result queues are per adapter, one adapter serving one `Cpu`, and the destructor gives back the table slots of undelivered results.
- **The browser build**: CMake `REX86_BROWSER` and the preset `web-browser-release`, linking the test tools without the Node file system, delivering the exit code to the page, with the trace corpus embedded.
- **The browser runner** (`tests/host/web/`): a page running the tools one after another in Workers, only the asynchronous test on the main thread; a LAN static server for real devices; a driver starting Chromium, Firefox and WebKit through Playwright 1.63.0; the real-device procedure in the guide.
- **The asynchronous test** `rex86_async_test`: two `Cpu`s on one frame loop, carrying on in the interpreter while installations are pending, each result checked against an interpreter-only run; it runs under wasm32's ctest (Node) and on browser main threads.
- **CI**: the job `browsers`.

## Findings

- Firefox (SpiderMonkey) refuses wasm installation from the 16,349th module in a process, a dropped module's code memory returning only at a garbage collection (record section 3).
- The current one-module-per-block backend is therefore bounded in Firefox by some 16,000 translated blocks; refused blocks run on the interpreter, so results stay correct. Batched installation and a module count budget are #49.

## Consumer impact

- The public contract (`include/rex86/`) does not change.
- A web consumer translating on the main thread uses `AsyncWebWasmModuleServices` and calls `Poll` after `Run` every frame; Worker consumers keep the synchronous adapter.
- In Firefox, a guest with many translated blocks can meet the module count limit (#49).
- **v0.0.22 and this release carry #50's defect** (the campaign section below), only with translation on; the default (off) is unaffected. Consumers' tag bumps wait for the patch release fixing #50 and its green campaign.

## Resolved issues

- [#48](https://github.com/reexec/rex86/issues/48) Validating wasm translation in real browsers, the asynchronous installer and browser CI : PR #51

The previous release, v0.0.22, is squash commit `2afcabc`.

## The previous release's campaign (v0.0.22)

Run 38063377276: **failed**. Ten of twelve jobs passed; two failed, filed as #50.

- **robust-release** (x86-64 Release, AMD EPYC 7763): one I8 violation in 1M cases (seed 2200826386). Translation faults 260 instructions earlier than the interpreter, at a different address; it reproduces locally.
- **wasm-translate**: the runner lost communication during the IR differential step, leaving no log, cause unresolved.

## Validation

- **The browser suite** (10 tests): Chromium 153 10/10 five times and Firefox 155 10/10 six times locally, WebKit 26.6 10/10 in CI; the unit tests', trace corpus', IR differential's, robustness' and asynchronous test's lines equal Node's.
- **The asynchronous installer**: a deliberate defect (no per-adapter queues) is caught by the test.
- **Performance** (AMD Ryzen 5 5600X, medians of three interleaved runs): wasm translation against the interpreter on alu, Chromium 8.9 times (216.0 MIPS) and Firefox 9.9 times (227.3 MIPS); call 4.7 and 3.8.
- **ctest** (`-Werror`): ordinary wasm32 7/7, forced `WASM` 7/7 and x86-64 Release 8/8 locally; CI on five hosts, the libFuzzer job and the `browsers` job are green.
