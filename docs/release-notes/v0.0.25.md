# rex86 v0.0.25

반복 사이에서 끊긴 REP 문자열 명령이 자기 바이트를 덮어쓴 경우에도, 끊어 실행한 결과가 한 번에 실행한 결과와 같아졌습니다. 번역을 켰을 때의 I8 위반(#50)이 이것으로 고쳐졌습니다. wasm 캠페인 작업은 Node 24로 돕니다. 공개 계약의 함수와 형은 바뀌지 않습니다.

## 변경 사항

- **진행 중인 REP의 재개**(#50, 설계 결정 1):
  - REP 문자열이 예산, 정지 요청, 번역의 내부 경계 때문에 반복 사이에서 끊기면(`kPartial`), `Cpu`가 그 명령의 디코드를 저장합니다.
  - 같은 CS:EIP와 같은 CS 모드에서 이어 갈 때는 메모리를 다시 읽지 않고 저장한 디코드로 실행합니다. 그래서 반복이 자기 바이트를 덮어써도 결과가 바뀌지 않습니다.
  - 인터럽트 처리기를 거쳤거나, 호스트가 EIP나 CS 모드를 바꿨거나, REP 도중 폴트 뒤에 다시 실행하면 지금처럼 다시 읽습니다. 하드웨어가 처리기에서 돌아올 때 하는 동작입니다.
  - 핫 루프에는 분기가 늘지 않습니다. 저장된 디코드로 실행하는 첫 단계는 루프 밖에서 처리합니다.
- **wasm 캠페인 작업**(#50, 설계 결정 2): `wasm-translate`가 `actions/setup-node`로 Node 24를 설치합니다.
- **README**: "번역 백엔드는 아직 없다"는 오래된 경고를 고쳤습니다(번역 첫 판이 있고 기본은 꺼짐).
- **#52 후속 기록**: 실제 브라우저 세션(Edge)의 비교에서 나온 거짓 개선 표시와 그 재현 시도를 #52 작업 로그와 설계에 적었습니다.

## 발견

- I8 위반의 원인은 번역기가 아니라 #32의 REP 재개 방식이었습니다. 번역 없이 예산을 1이나 2로 나눠도 재현됩니다. 번역기는 저장 뒤 "다음 한 단계만 인터프리터로" 실행하면서 REP 한가운데에 경계를 만들어 이를 드러냈습니다.
- `wasm-translate`가 세 번 연속 끊긴 것은 러너의 Node 20 때문으로 봅니다. 같은 shard(50만 건)가 Node 20.18에서는 25분 동안 끝나지 않고 메모리가 4.4 GB까지 늘었습니다. Node 24.19에서는 137초, 최대 168 MB였습니다. 캠페인은 shard 넷을 동시에 돌립니다.

## 소비자 영향

- 공개 계약(`include/rex86/`)의 함수와 형은 바뀌지 않습니다. `Cpu`에 비공개 멤버가 늘었으므로 소스에서 다시 빌드합니다(FetchContent 그대로).
- 의미가 바뀌는 곳은 하나입니다. REP가 `Run` 경계에서 끊긴 뒤 호스트가 EIP를 그대로 두고 그 명령의 바이트를 고치면, 이제 고친 바이트가 아니라 시작한 명령이 이어 갑니다. 다시 읽게 하려면 EIP나 CS를 바꿉니다. 두 소비자의 HLE는 실행 중인 REP의 바이트를 고치지 않으므로 영향이 없다고 봅니다(추정).
- 번역을 켠 소비자에게 v0.0.22~v0.0.24에 있던 #50 결함이 사라집니다. 소비자의 tag 올림은 이 판의 캠페인이 녹색인지 본 뒤에 합니다.

## English

# rex86 v0.0.25

A REP string stopped between iterations now ends the same in pieces as at once even when it overwrites its own bytes, which fixes the I8 violation with translation on (#50). The wasm campaign job runs on Node 24. The public contract's functions and types do not change.

## Changes

- **Resuming a REP in progress** (#50, design decision 1): when a REP string stops between iterations (`kPartial`) at the budget, a stop request or translation's internal boundary, the `Cpu` saves its decode and, resuming at the same CS:EIP and CS mode, runs from it rather than memory read again, so iterations overwriting the instruction's own bytes no longer change the result; after an interrupt handler, a host changing EIP or CS's mode, or a fault mid-REP, it is read again as before, as the hardware does returning from a handler; the hot loop gains no branch, the saved decode's first step running outside it.
- **The wasm campaign job** (#50, design decision 2): `wasm-translate` installs Node 24 with `actions/setup-node`.
- **README**: the stale warning that translation backends do not exist yet is fixed (translation's first version exists, off by default).
- **#52 follow-up record**: a false improvement mark from a real browser session (Edge) and the attempts to reproduce it, in #52's work log and design.

## Findings

- The I8 violation came from #32's way of resuming a REP, not from translation: it reproduces without translation when a run is split at budgets of 1 or 2; translation exposed it by running "the next single step on the interpreter" after a store, which split a REP.
- `wasm-translate`'s three stalls are attributed to the runner's Node 20: one 500,000-case shard did not finish in 25 minutes under Node 20.18, memory rising to 4.4 GB, where Node 24.19 took 137 seconds at 168 MB peak; the campaign runs four shards at once.

## Consumer impact

- The public contract's (`include/rex86/`) functions and types do not change; `Cpu` gains private members, so rebuild from source (FetchContent as before).
- One meaning changes: after a REP stopped at a `Run` boundary, a host that edits the instruction's bytes leaving EIP alone now sees the started instruction continue rather than the edited bytes; to have them read again, change EIP or CS. Neither consumer's HLE edits a running REP's bytes, so no effect is expected (inferred).
- Consumers with translation on lose #50's defect, present from v0.0.22 to v0.0.24; consumers' tag bumps follow a green campaign for this version.

## Validation

- **New tests**: the split equivalence of three self-overwriting REPs (STOSB, STOSD with DF=1, MOVSB), the same programs under translation (evaluator) against the interpreter, resuming after EIP or CS's mode changed, and the `seed=2200826386` regression; 52 checks fail on the code before the change and pass after.
- **Robustness** (Windows x64 MSVC Release): `--case 2200826386` gives `result=ok`, and 200,000 cases have no violation.
- **ctest**: Windows x64 Release 6/6, wasm32 (Node 24) 7/7.
- **The wasm IR differential** (Node 24, one 500,000-case shard): no mismatch, 137 seconds.
- **Performance** (AMD Ryzen 5 5600X, Windows x64 MSVC Release, medians of three runs interleaved with `main`): string 0.97 (the pre-change runs themselves spanning 68.2 to 75.8 MIPS), mixed 1.04, alu 1.21; alu uses no REP, so a code layout effect is inferred, cause unchecked; no regression.
