# rex86 v0.0.19

실행 예산의 단위를 "단계"로 바꿨습니다. REP 문자열은 반복 하나가 한 단계이고, 그 밖의 명령은 명령 하나가 한 단계입니다. 그래서 긴 REP 문자열 도중에도 `Run(budget)`이 예산에서 돌아오고, `RequestStop`과 대기 인터럽트를 반복 사이에서 처리합니다. 하드웨어가 REP를 인터럽트로 멈추는 지점, 즉 트랩 플래그 단일 스텝의 단위와 같습니다. 아키텍처 결과는 바뀌지 않습니다.

## 변경 사항

- **공개 계약**(#32):
  - `Event::instructions_retired`가 `Event::steps`가 됐습니다.
  - `Cpu::Run(std::uint64_t step_budget)`: 인자 이름과 뜻이 바뀌었습니다(ABI는 같음).
  - `Cpu::Step()`은 이제 한 단계를 실행합니다. 반복 도중의 REP에서는 반복 하나입니다.
  - `Cpu::InstructionInProgress()`를 더했습니다. 반복 사이에서 멈춘 REP가 있는지 알려 줍니다.
- **인터프리터**(#32):
  - REP 문자열은 반복마다 단계를 세고, 한도에 닿거나 `attention`이 서면 반복 사이에서 멈춥니다(`StepStatus::kPartial`). EIP는 문자열 명령에 그대로 있고, 레지스터는 마지막 반복 뒤 상태입니다.
  - 반복 도중의 폴트와 거절된 INS/OUTS는 끝낸 반복을 단계로 셉니다.
  - 대기 인터럽트는 반복 사이에서 전달되고(복귀 EIP는 문자열 명령), IRET 뒤에 나머지 반복이 이어집니다.
  - `Cpu`는 진행 중인 REP 위치에서 게이트 검사를 건너뜁니다. 호스트가 EIP를 옮기면 다시 검사합니다.
  - 예산은 `RunBlock`이 스택에 둔 `StepBudget`을 `StepResult`로 빌려줍니다. 측정으로 정한 형태이며, REP가 아닌 명령의 비용은 단계당 호스트 명령 약 2개 늘었습니다.
- **하네스**(#32): trace 재생의 단일 스텝 모드는 `InstructionInProgress()`가 거짓이 될 때까지 `Step()`을 되풀이해 명령 하나를 끝까지 실행합니다. 벤치마크, 견고성 하네스, probe는 단계를 셉니다(출력 키 이름은 그대로).
- **결함 수정**(#32 중 발견): `GuestMemory::HostPointer`가 정체 매핑(null base)에서 null 포인터 산술을 했습니다. Clang의 UBSan이 잡았고, 이제 주소를 정수로 더합니다.
- **문서**: #32의 설계, 지시서, 작업 로그를 썼습니다. ARCHITECTURE, README(목표 8, 현재 수치), 분석 `interpreter-performance.md`(2.3절), kb `trap-flag-single-step.md`, 벤치마크 가이드를 갱신했습니다.

## 소비자 영향

- 공개 계약이 바뀌었으므로 소비자는 다시 빌드해야 합니다. `Event::instructions_retired`를 쓰는 코드는 `Event::steps`로 고칩니다.
- 프레임 예산은 단계 단위입니다. REP 문자열이 반복마다 세지므로 같은 예산이 기준 CPU의 시간에 더 가깝습니다.
- `kBudgetExhausted`는 REP 반복 도중에도 올 수 있습니다. 그때 EIP는 문자열 명령을 가리키고, 다음 `Run`이 이어서 실행합니다. 호스트가 이 상태의 EIP로 판단하려면(예: "EIP가 게이트 주소면") `InstructionInProgress()`를 함께 봐야 합니다.
- 두 소비자 저장소는 아직 rex86을 쓰지 않으므로(2A, 2B단계 전) tag 올림 작업은 그때 시작합니다.

## English

# rex86 v0.0.19

The execution budget's unit is now the step: one iteration of a REP string, one instruction otherwise. So `Run(budget)` returns at its budget even inside a long REP string, and handles `RequestStop` and pending interrupts between iterations. That is where the hardware stops a REP for an interrupt, the unit of a trap-flag single step. Architectural results do not change.

## Changes

- **The public contract** (#32):
  - `Event::instructions_retired` became `Event::steps`.
  - `Cpu::Run(std::uint64_t step_budget)`: the argument's name and meaning changed (same ABI).
  - `Cpu::Step()` now runs one step, one iteration of a REP in progress.
  - `Cpu::InstructionInProgress()` is new. It tells whether a REP stopped between iterations.
- **The interpreter** (#32):
  - A REP string counts a step per iteration and stops between iterations once the limit is reached or `attention` is raised (`StepStatus::kPartial`), with EIP still at the string instruction and the registers as the last iteration left them.
  - A mid-string fault or a declined INS/OUTS counts the iterations it completed.
  - A pending interrupt is delivered between iterations (the return EIP is the string instruction), and the remaining iterations continue after IRET.
  - The `Cpu` skips the gate check at the position of a REP in progress, and checks again once the host moves EIP.
  - `RunBlock` lends the budget, a `StepBudget` on its stack, through the `StepResult`. The form was chosen by measurement; instructions other than REP strings cost about 2 more host instructions per step.
- **Harnesses** (#32): trace replay's single-step mode repeats `Step()` until `InstructionInProgress()` is false, running one whole instruction. The benchmark, robustness harness and probe count steps (their output keys keep their names).
- **A defect fixed** (found during #32): `GuestMemory::HostPointer` did pointer arithmetic on null for the identity mapping (null base). Clang's UBSan caught it; the address is now added as an integer.
- **Documents**: the #32 design, work order and work log. ARCHITECTURE, README (goal 8, current figures), the analysis `interpreter-performance.md` (section 2.3), the kb `trap-flag-single-step.md` and the benchmark guide were updated.

## Consumer impact

- The public contract changed, so consumers must rebuild. Code using `Event::instructions_retired` moves to `Event::steps`.
- Frame budgets count steps. As REP strings count per iteration, the same budget tracks the reference CPU's time more closely.
- `kBudgetExhausted` can arrive in the middle of a REP. EIP then addresses the string instruction, and the next `Run` continues it. A host judging by EIP in that state (say, "EIP is at a gate address") must also look at `InstructionInProgress()`.
- Neither consumer repository uses rex86 yet (phases 2A and 2B not started), so the tag-bump tasks start then.
