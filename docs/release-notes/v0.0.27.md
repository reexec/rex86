# rex86 v0.0.27

정수 호스트 대조 fuzz의 세그폴트([#53](https://github.com/reexec/rex86/issues/53))를 고친 patch 릴리스입니다. 코어는 바뀌지 않았습니다.

## 변경 사항

- **`rex86_int_fuzz`의 대체 신호 스택에 `SS_AUTODISARM`**: 시험 명령이 ESP를 대체 신호 스택 안으로 옮기면 신호 전달이 실패해 프로세스가 조용히 죽었습니다. 이제 커널이 늘 대체 스택의 꼭대기로 바꿉니다. 하네스는 `siglongjmp`로 처리기를 나오므로 시험마다 대체 스택을 다시 등록합니다. 이 플래그를 거절하는 커널(Linux 4.7 전)에서는 시작할 때 실패를 알립니다.
- **문서**: #53 설계 결정 3, 작업 로그, kb `trap-flag-single-step.md`의 대체 신호 스택 항목.

## 발견

v0.0.26 캠페인의 core 두 개를 읽어 v0.0.23부터 이어진 세그폴트의 원인을 확인했습니다.
- 시험 명령 `mov esp, imm32`(사례 1,370,060)와 `add esp, [mem]`(사례 3,765,805)이 ESP를 힙에 `malloc`으로 잡은 대체 신호 스택의 바닥 근처로 옮겼습니다.
- 그러자 커널은 이미 대체 스택 위에 있다고 보고, 그 ESP 아래에 프레임을 쌓다가 넘쳤습니다. 그래서 처리기 없이 프로세스를 끝냈습니다.
- 힙 주소는 ASLR로 바뀌므로 시드로는 재현되지 않았습니다.
- 작은 재현 프로그램에서, 기존 설정은 종료 코드 139로 끝났고 `SS_AUTODISARM`에서는 처리기가 실행됐습니다.

## English

# rex86 v0.0.27

A patch release fixing the integer host-comparison fuzz's segfault (#53). The core is unchanged.

## Changes

- **`SS_AUTODISARM` on `rex86_int_fuzz`'s alternate signal stack**: when a tested instruction moved ESP into the alternate signal stack, signal delivery failed and the process died silently; the kernel now always switches to the stack's top. The harness leaves the handler through `siglongjmp`, so it re-arms the stack before every test, and a kernel refusing the flag (before Linux 4.7) makes it fail at start.
- **Documents**: #53's design decision 3, the work log and the alternate-stack note in the kb page `trap-flag-single-step.md`.

## Findings

Two cores from v0.0.26's campaign show the cause of the segfault seen since v0.0.23:
- The tested `mov esp, imm32` (case 1,370,060) and `add esp, [mem]` (case 3,765,805) moved ESP near the bottom of the alternate signal stack `malloc` had placed on the heap.
- The kernel, taking the process to be on that stack already, built the frame below that ESP, overflowed, and ended the process without the handler.
- ASLR moves the heap, so seeds never reproduced it.
- A small program reproduces it: exit code 139 as before, and the handler runs under `SS_AUTODISARM`.

## Consumer impact

- None. The core and the public contract equal v0.0.26's.

## Resolved issues

- [#53](https://github.com/reexec/rex86/issues/53) v0.0.23 campaign failure: int-i386 CMPS fault kind mismatches (EPYC 9V45) and a harness segfault : PR #56, PR #57. It closes once this tag's campaign shows int-i386 green.

The previous release, v0.0.26, is squash commit `5dfe311`.

## The previous release's campaign (v0.0.26)

Run 38214393370: **failure**, with 10 of 12 jobs passing.
- **int-i386 translate and warmup-default**: shard 0 of each died of signal 11 on AMD EPYC 7763 runners. The observability added in v0.0.26 kept the cores and binary, which revealed the cause (above).
- No CMPS mismatch appeared. With no Zen 5 runner, the widened judgment was not yet exercised.
- Passed: int-i386 warmup-0, robust-release, robust-asan, robust-arm64, libfuzzer, irdiff-x64, sst, x87-simd, wasm-translate and plan.

## Validation

- **Reproduction program** (i386, WSL2 kernel 6.18): ESP at the alternate stack's bottom + 64 followed by an INT3 ends with exit code 139 as before, and with `SS_AUTODISARM` plus re-arming the handler runs all three times.
- **Integer fuzz** (Intel Core i5-7200U, i386 Release): the two seeds that died in v0.0.26 (2695000000 with `--translate`, 2630000000) ran 5 million cases each with zero mismatches and a normal exit.
- **ctest**: i386 Debug 9/9.
