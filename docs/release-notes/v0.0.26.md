# rex86 v0.0.26

v0.0.23 캠페인의 int-i386 실패([#53](https://github.com/reexec/rex86/issues/53))를 다룬 patch 릴리스입니다. 코어는 바뀌지 않았습니다. 정수 호스트 대조 fuzz의 판정과 진단, 캠페인 워크플로가 바뀌었습니다.

## 변경 사항

- **CMPS 판정**: #40이 분류한 Zen 5 이탈이 있습니다. CMPS의 원본이 null 세그먼트이면 Zen 5는 원본을 먼저 봐서 #GP를 내고, 코어는 목적지를 먼저 봐서 #PF를 냅니다. 이제 목적지의 일부라도 닿지 못하면 이 이탈로 셉니다. v0.0.23의 5건은 목적지가 매핑 영역 끝(0x12FFD~0x12FFF)에 걸쳐 있었는데, 지금까지의 판정은 시작 주소가 영역 밖일 때만 셌습니다.
- **`rex86_int_fuzz` 진단**:
  - 줄 단위 stdout.
  - `--progress N`(`progress case=… so_far=…`)과 `--from N`(앞의 N건은 생성만 하고 건너뜀).
  - 실행 중인 사례 번호와 바이트를 기록합니다.
  - 신호 처리기 재진입을 알리고 종료 코드 97로 끝냅니다.
  - 게스트 바깥의 폴트도 사례 번호와 바이트를 남깁니다.
- **캠페인**:
  - int-i386 작업이 core 파일과 바이너리를 아티팩트에 남기고, `--progress 250000`을 줍니다.
  - `fuzz_campaign.sh`는 신호로 죽은 샤드를 `died of signal N`으로 알리고, gdb가 있으면 백트레이스를 붙입니다.
- **문서**: #53 설계, 지시서, 작업 로그, 분석 `integer-host-comparison.md`, 가이드 `integer-host-fuzz-and-traces.md`.

## 발견

- **세그폴트(종료 코드 139) 두 샤드는 시드로 재현되지 않습니다.**
  - Intel Kaby Lake(WSL2)에서 v0.0.23 translate 실행은 9번 중 1번 죽었습니다. 같은 바이너리, 같은 시드를 다시 돌리면 정상이었습니다.
  - 현재 코어로는 한 번도 재현되지 않았습니다.
  - 같은 500만 입력을 코어로만 재생한 ASan/UBSan 실행은 v0.0.23 코어와 현재 코어 모두 보고가 0건입니다.
  - 그래서 하네스의 네이티브 실행 쪽(신호 전달, 커널, 러너 CPU)에서 드물게 일어나는 일로 추정하고, 원인은 미확정으로 둡니다. 이 판의 캠페인부터는 다시 일어나면 진행 줄, 빵부스러기, core, 백트레이스가 남습니다.

# rex86 v0.0.26

A patch release for v0.0.23's campaign failure in int-i386 (#53). The core is unchanged; the integer host-comparison fuzz's judgment and diagnostics and the campaign workflow change.

## Changes

- **CMPS judgment**: #40 classified a Zen 5 deviation: when a CMPS source has a null segment, Zen 5 checks the source first and raises #GP, while the core checks the destination first and raises #PF. That deviation now counts whenever any part of the destination is unreachable. v0.0.23's five cases had a destination straddling the mapped region's end (0x12FFD to 0x12FFF), and the old judgment counted only destinations starting outside the region.
- **`rex86_int_fuzz` diagnostics**:
  - Line-buffered stdout.
  - `--progress N` (`progress case=… so_far=…`) and `--from N` (generate and skip the first N cases).
  - The running case's number and bytes are recorded.
  - A signal re-entering the handler is reported, ending with exit code 97.
  - A fault outside the guest also reports the case number and bytes.
- **Campaign**:
  - The int-i386 jobs keep core files and the binary in their artifacts and pass `--progress 250000`.
  - `fuzz_campaign.sh` names a shard killed by a signal (`died of signal N`) and appends a gdb backtrace when it can.
- **Documents**: the #53 design, work order and work log, the analysis `integer-host-comparison.md` and the guide `integer-host-fuzz-and-traces.md`.

## Findings

- **The two segfaulting shards (exit code 139) do not reproduce by seed.**
  - On an Intel Kaby Lake (WSL2), v0.0.23's translate run died in 1 of 9 tries; the same binary and seed then ran clean.
  - Today's core never died.
  - Core-only ASan/UBSan replays of the same five million inputs report nothing for v0.0.23's core or today's.
  - The cause is therefore inferred to be a rare event on the harness's native side (signal delivery, kernel, runner CPU) and is left unresolved. From this release's campaign on, a recurrence leaves progress lines, breadcrumbs, a core and a backtrace.

## Consumer impact

- None. The core and the public contract equal v0.0.25's.

## Validation

- **Reproduction and attribution** (Intel Core i5-7200U Kaby Lake, WSL2, the campaign's i386 Release):
  - Both seeds rerun, and v0.0.23's source run 9 times (2 of them without ASLR).
  - A generate-only input scan and 3 million POPFD cases.
  - Two core-only ASan/UBSan replays of 5 million cases each.
- **ctest**: i386 Debug 9/9, integer fuzz and corpora included. 100,000 integer fuzz cases with zero mismatches.
- **Campaign paths**: `fuzz_campaign.sh` tested with a fake shard dying of a signal, and the workflow's YAML checked.
