# rex86 v0.0.32

wasm 번역 경로가 빨라졌습니다([#65](https://github.com/reexec/rex86/issues/65)). 블록 하나의 비용을 측정해 보니, 번역된 블록의 본체는 시간의 4분의 1 남짓이었습니다. 나머지는 블록 사이의 디스패치와 메모리 검사 도우미 호출이었습니다. 이 둘을 줄여, 번역 범위 안의 워크로드가 v0.0.31보다 28~69% 빨라졌습니다.

## 변경 사항

- **디스패치 빠른 경로**:
  - 번역된 블록이 이어지는 동안 `Cpu::RunUntilStop`의 안쪽 고리가 다음 블록을 바로 돌립니다. 정지 요청과 대기 인터럽트는 주의 신호(attention)로, 게이트는 게이트 필터로 거르고, 예산과 모드를 봅니다. 하나라도 걸리면 원래의 검사로 돌아갑니다. 게이트가 등록된 소비자도 빠른 경로를 씁니다.
  - `Translator::Lookup` 앞에 EIP로 바로 찾는 1,024칸 캐시를 뒀습니다. 다시 들어오는 번역 블록은 해시를 거치지 않습니다.
  - `ModesSupported`, `PageAttributeTable::Generation`, 캐시가 맞는 경우의 `Lookup`을 인라인으로 옮겼습니다.
- **인라인 메모리 검사**: 생성된 wasm이 흔한 경우를 직접 판단합니다. 세그먼트가 평탄하고(쓰기라면 쓰기 가능), 범위가 메모리 안이고, 첫 페이지와 마지막 페이지의 속성이 맞는 경우입니다. 그 밖의 경우만 지금처럼 C++ 도우미가 판단합니다. 생성 코드는 속성 표의 주소와 메모리 크기를 백엔드의 작은 구조체(`CheckContext`)에서 읽습니다.
- **공개 계약**: `PageAttributeTable::data()`(속성 바이트 배열, 읽기 전용)를 더했고, `PageAttributeTable::Generation`이 헤더의 인라인 정의가 되었습니다. 둘 다 소스 호환입니다.
- **시험**: `WasmCheckTests`가 인라인 검사의 경계 아홉 경우에서 번역 실행과 인터프리터의 이벤트, 상태, 메모리가 같은지 봅니다. 읽기 전용 페이지, 매핑되지 않은 다음 페이지로 걸침, 메모리 끝, 번역된 코드 페이지에 쓰기, 평탄하지 않은 DS 등입니다.
- **문서**: #65 설계, 작업 지시서, 작업 로그, [인터프리터 성능 분석](../analysis/interpreter-performance.md) 2.6절, ARCHITECTURE.

## 발견

- **블록 하나의 비용**(v0.0.31, Node, wasm): alu 블록은 약 180 ns, memory와 call 블록은 약 120 ns였습니다. 그 가운데 본체는 23~26%뿐이었습니다. 디스패치가 32~42%, 메모리 검사 도우미가 memory 18%와 call 30%였습니다.
- **측정 방법**: Emscripten의 링크 최적화가 함수를 합치고 인라인해, 디스패치 안을 나누기 어려웠습니다. 링크만 `-O0`으로 한 빌드(각 파일은 `-O3`)의 CPU 프로파일로 함수별로 나눴습니다.
- **결과**(같은 시간에 번갈아 일곱 번 돌린 최고값, wasm, 측정 기계에 다른 부하가 있었음):

  | 워크로드 | v0.0.31 | v0.0.32 | 변화 |
  |---|---:|---:|---:|
  | alu | 44.1 | 56.2 | +28% |
  | memory | 28.7 | 39.3 | +37% |
  | call | 25.6 | 43.4 | +69% |
  | blocks | 1.91 | 1.87 | — |
  | mixed | 14.6 | 15.5 | +6% |

- **남은 것**: call과 memory에서 디스패치가 아직 약 30%입니다. 더 줄이려면 블록 연결이 필요합니다. `mixed`는 인터프리터(x87, REP 문자열)가 지배합니다.

## 소비자 영향

- 결과는 그대로이고, 번역이 켜진 소비자에서 블록 사이와 메모리 접근의 비용이 줄었습니다.
- 공개 계약에는 소스 호환인 변화만 있습니다(위).

## English

# rex86 v0.0.32

The wasm translation path got faster (#65). Measuring one block's cost showed a translated block's body at about a quarter of its time, the rest being dispatch between blocks and calls to the memory-check helper; cutting both made the workloads inside the translation coverage 28 to 69% faster than v0.0.31.

## Changes

- **A dispatch fast path**:
  - While translated blocks follow one another, an inner loop in `Cpu::RunUntilStop` runs the next one directly. Stop requests and pending interrupts are caught by attention, gates by the gate filter, and the budget and modes are checked; any of them sends it back through the original checks, so consumers with gates registered keep the fast path.
  - A 1,024-slot cache indexed by EIP sits in front of `Translator::Lookup`, so a translated block entered again skips the hash.
  - `ModesSupported`, `PageAttributeTable::Generation` and `Lookup`'s cache path became inline.
- **Inline memory checks**: generated wasm judges the common case itself (a flat segment, writable for a write, the range inside memory, and the first and last pages with the right flags), the C++ helper judging the rest as before. Generated code reads the flags' address and the memory size from a small structure in the backend (`CheckContext`).
- **Public contract**: `PageAttributeTable::data()` (the read-only array of flag bytes) is added, and `PageAttributeTable::Generation` became an inline definition in the header; both are source compatible.
- **Tests**: `WasmCheckTests` checks that a translated run's events, state and memory equal the interpreter's in nine edge cases of the inline check, such as a read-only page, a straddle into an unmapped page, the end of memory, a write into a translated code page and a non-flat DS.
- **Documents**: #65's design, work order and work log, section 2.6 of the interpreter performance analysis, and ARCHITECTURE.

## Findings

- **One block's cost** (v0.0.31, Node, wasm): some 180 ns for an alu block and 120 ns for memory and call blocks, of which the body was only 23 to 26%; dispatch took 32 to 42% and the memory-check helper 18% on memory and 30% on call.
- **How it was measured**: Emscripten's link-time optimizer merges and inlines functions, hiding dispatch's parts; CPU profiles of a build linked at `-O0` (each file still at `-O3`) split it by function.
- **Results** (the best of seven interleaved runs taken at the same time, wasm, with other load on the measuring machine): alu 44.1 to 56.2 (+28%), memory 28.7 to 39.3 (+37%), call 25.6 to 43.4 (+69%), blocks 1.91 to 1.87 (unchanged), mixed 14.6 to 15.5 (+6%).
- **Remaining**: dispatch is still some 30% on call and memory, and reducing it further takes block linking; `mixed` is dominated by the interpreter (x87, REP strings).

## Consumer impact

- Results stay; consumers with translation on pay less between blocks and for memory accesses.
- The public contract changes only in source-compatible ways (above).
